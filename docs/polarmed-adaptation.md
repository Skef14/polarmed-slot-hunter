# Адаптация для reg.polarmed.ru — состояние

Исходный проект polinalamponi/emias-slot-hunter скопирован целиком из ветки main (версия package.json: 0.1.5). Лицензия MIT и авторство сохранены. **Подготовлена экспериментальная адаптация свободной записи 0.3.2:** `dist/polarmed-slot-hunter.user.js`. Инструкция и ограничения: `README.polarmed.md`. Исходный `dist/emias-slot-hunter.user.js` работает только с ЕМИАС.

## Текущее состояние

В 0.3.2 по сообщению пользователя исправлена обязательность `history_id`: отсутствие истории допустимо в свободной записи. Пустое значение нормализуется в `''` для списка врачей, списка талонов и подтверждения записи. Наличие пациента и защитных полей по-прежнему проверяется; идентификатор истории не подставляется из других пациентов или обращений. Добавлены сквозные тесты отсутствующего, null, пустого и пробельного значения.

Предоставленные структуры `/profile/` и `/signup/free/` исследованы. Подтверждены `/api/appointment_list/`, `/api/signup/`, формы пациента и выбора врача. Публичный `/static/js/create-claim.js` дополнительно подтверждает атрибуты записи в кабинете: `data-appointment-id`, `data-patient-id`, `data-clinic-id` на элементах `[data-claim]`. Эти элементы используются только для чтения при проверке результата, адреса отмены не вызываются.

Работают общий мастер, обязательный холостой прогон, фильтры, режим подтверждения, цикл с минимальным интервалом 20 секунд, уведомления и координация вкладок. Создан отдельный адаптер с CSRF/cookie-сессией сайта, Web Locks и устойчивым журналом попыток записи. Контекст берётся из загруженной модели или штатного выбора сайта; отдельная копия персональных данных охотником не сохраняется.

В 0.3.0 добавлен режим всей специальности: конкретный врач для инициализации не требуется. `/api/doctor_list/` опрашивается с `speciality_form-*`, затем последовательно вызывается `/api/appointment_list/` для каждого врача до первой подходящей находки. Кандидат хранит ID/имя врача, повторная проверка перед записью не может подменить его другим. Плашка явно обозначена кнопкой «Охотник: открыть настройки», при неготовом контексте открывается окно инструкции.

В 0.3.1 убрана жёсткая зависимость от единственного глобального `requirejs`: поддержаны `app`, AMD-загрузчики, чтение только нужных шагов, а также резервный путь через явно выбранный в hash `preset`, штатное Amplify-хранилище и DOM. Неполные/противоречивые данные не угадываются. Кнопка проверки получила состояние загрузки, ограничение времени и видимые нумерованные ошибки с безопасными кодами `P_…` вместо повторного показа той же инструкции без объяснения.

Сведения пользователя: отдельной страницы переноса нет; существующий талон отменяется отдельно. Автоматическая отмена **не реализована намеренно**. После новой записи старый талон отменяет сам пользователь, только проверив результат. Если сайт не разрешает новую запись при старой, скрипт останавливается без отмены.

Время существующей записи можно ввести вручную: это только верхняя граница поиска, не перенос. Другие записи/дорога автоматически не учитываются; направления, анализы, исследования и автоматическое продление сессии остаются за рамками этой версии. Проверка результата пока зависит от известных атрибутов записи в кабинете; если их нет или они изменились, выдаётся требование ручной проверки, а не ложный успех.

**Проверки на сервере с созданием реальных медицинских записей не выполнялись.** Автоматические тесты используют искусственные ответы и изолированную имитацию модели сайта.

## Что установлено по публичному сайту

- Вход: `/login/esia/`. Авторизация выполняется пользователем на самом сайте.
- Публичное расписание: `/schedule/`.
- Клиент расписания: `/static/js/app/schedule-built.js` (Backbone, jQuery).
- Списки и расписание запрашиваются POST-запросами с form-urlencoded, а не через JSON API ЕМИАС.
- Формы: `/api/clinic_list/`, `/api/speciality_list/`, `/api/doctor_list/`, `/api/doctor_schedule/`.
- Поля расписания: `doctor_form-doctor_id`, `doctor_form-clinic_id`, `doctor_form-n3_session`, `doctor_form-n3_session_expired_time`, `doctor_form-patient_id`, `doctor_form-history_id`, `doctor_form-appointment_type`.
- Ответ расписания, судя по публичному клиенту: `{success, response: [недели], error}`. Элементы содержат `date_start`, `date_end`, `deny`, `denyCause`. Это интервалы расписания, **не доказательство наличия доступного для записи талона**.
- Список врачей: `IdDoc`, `Name`, `CountFreeParticipantIE`, `AriaNumber`.
- Список специальностей: `IdSpesiality`, `NameSpesiality`.
- Список учреждений: `IdLPU`, `LPUFullName`, `Address`.

## Что необходимо для продолжения

### Исследованы предоставленные файлы data-site

`singup-build.js` содержит клиент записи. Важные отличия от публичного расписания:

- `AppointmentSelectForm` получает `response` как словарь дней `YYYY-MM-DD` с массивами талонов `{id, date_start, date_end}`. Поля времени включают `iso` и `time`.
- `SingUpValidateForm.collectData()` отправляет `appointment_form-clinic_id`, `appointment_form-history_id`, `appointment_form-patient_id`, `appointment_form-appointment_id`, `appointment_form-n3_session`, `appointment_form-n3_session_expired_time`, `appointment_form-referal_id` и `csrfmiddlewaretoken`.
- Адрес подтверждения берётся из `action` формы страницы, а не зашит в JS.
- `/signup/create-appointment/` вызывается **после** успешного основного запроса и передаёт сведения о записи. Его нельзя принять за единственный запрос бронирования.
- `preset` в URL — ключ временно сохранённых данных пациента в хранилище сайта, а не постоянный идентификатор врача. В исходники его переносить не нужно.
- Представленный клиент не описывает отдельный сценарий переноса и получение списка текущих записей.

Добавлен `adapters/polarmed.js`: разбор врачей/талонов, проверки времени UTC+3 и структуры ответов, подготовка полей подтверждения. Сетевое взаимодействие реализовано отдельно в `adapters/polarmed-platform.js` и подключено к общему ядру через параметр `platform`. Тесты используют искусственные ответы, не реальные записи.

### Как повторно собрать структуру при изменении сайта (для диагностики)

1. В Tampermonkey создайте новый скрипт, замените весь шаблон содержимым `dist/polarmed-site-inspector.user.js` и сохраните. При необходимости разрешите пользовательские скрипты в настройках расширения браузера.
2. Обновите reg.polarmed.ru. Внизу справа появится кнопка «Polarmed: сохранить структуру».
3. Войдите на сайте обычным способом. Откройте `/profile/` и нажмите кнопку. Сохранится JSON-файл.
4. Откройте запись, выберите поликлинику, специальность и врача, дойдите до списка времени. Снова сохраните структуру. Если слотов нет, всё равно сохраните отчёт.
5. Если есть обычная страница переноса существующей записи, можно открыть её и сохранить ещё один отчёт. **Не отменяйте запись и не подтверждайте новую запись ради диагностики.**
6. Положите полученные `polarmed-structure-*.json` в `data-site`. Если там обнаружатся другие клиентские JS-файлы, добавьте их тоже.

Сборщик не обращается к сети и ничего не записывает в хранилище сайта. Он экспортирует только имена полей, методы/пути форм, известные имена представлений, пути скриптов и ссылки разделов записи. Значения полей, cookie, текст страницы, содержимое localStorage, query и hash URL не экспортируются; динамические сегменты пути заменяются на `[value]`. Перед передачей файл можно открыть и проверить.

Пересобрать сборщик: `npm run build:inspector`. Исходный `dist/emias-slot-hunter.user.js` остаётся неизменным по назначению и работает только с ЕМИАС.

Если их недостаточно, нужны обезличенные примеры запросов/ответов: список текущих записей, направления, доступные талоны, создание и перенос записи, проверка результата. Примеры создания/переноса — только от обычных действий пользователя, если он действительно собирался их выполнять; не нужно делать медицинские записи ради тестирования.

Не передавайте пароль Госуслуг, cookie, Authorization, CSRF-токены, n3_session, ФИО, полис, СНИЛС, дату рождения, идентификаторы пациента или необработанный HAR. Все идентификаторы в примерах заменяются согласованными вымышленными значениями.

## Реализовано и дальнейшая проверка

1. Реализован адаптер свободной записи: контекст сайта, обнаружение выбранного врача, поиск талонов, новая запись, независимая проверка результата. Отмена и отдельный перенос не реализуются.
2. Используются общие фильтры, мастер, обязательный холостой прогон, подтверждение, журналирование, уведомления и координация вкладок. Ограничения явно описаны в `README.polarmed.md`.
3. Подготовлены отдельные метаданные, ключи хранения и сборка `dist/polarmed-slot-hunter.user.js`, без автоматических обновлений из исходного репозитория ЕМИАС.
4. Добавлены тесты на искусственных ответах, потере ответа, смене пациента, гонке вкладок, остановке и сохранении блокировки после перезагрузки. Сохранены минимальный интервал 20 секунд и сетевые паузы.
5. Остаётся ручная проверка в браузере пользователя: загрузка контекста, холостой прогон, затем только при действительно нужной записи — обычное использование и проверка результата. Не обходить ЕСИА/капчу, не делать записи ради теста и не отменять старый талон заранее.
